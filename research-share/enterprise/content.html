02 / 目标架构

一条调用链，两个网关边界。

箭头表示请求方向，结果沿调用链返回。网关是本设计中的逻辑角色，具体产品与部署方式尚未确定。

身份入口

AI Gateway

确认企业用户是谁，将既有身份转换为智能体可使用的身份上下文，并限定可使用的能力。

职责边界

复用企业身份和权限来源；不另建一套与业务系统脱节的用户权限。

依据：原文 §3.1

接入层治理共性调用，业务服务执行数据与业务约束。原文 §2—§4；最终数据权限、脱敏、审批和业务规则的接口分工仍需落地明确。

03 / 职责划分

入口管身份，执行层管任务，
出口管调用。

进入智能体之前

AI Gateway

谁能进入，能使用哪些能力。

  • 用户认证与身份转换
  • 智能体能力授权
  • 会话初始化、用户行为审计
任务执行过程中

DSH Runtime

在获准范围内组织执行。

  • 任务规划与推进
  • 插件、技能与工具调用
  • 会话记录与管理
调用企业能力之前

MCP Gateway

本次调用哪个工具，是否获准。

  • 身份凭据校验、工具权限
  • 按策略检查声明的范围
  • 调用审计、限流与安全策略
复用已有业务系统

数据与业务约束继续生效

组织与数据权限 · 数据脱敏 · 操作授权 · 审批权限 · 业务规则

具体检查落点与接口契约
仍需确认
插件、技能、工具和会话，在本设计中分别指什么？

插件（Plugin）装配可扩展能力与业务连接。

技能（Skill）提供专业方法、指令和参考内容。

工具（Tool）执行具体查询、计算或业务动作。

会话（Session）组织一段用户交互及其执行上下文。

企业权限由可信网关与业务服务承接，DSH 保持通用。原文 §3、§4。运行时的工具、插件、凭据和网络访问边界也需配置，避免绕开受控能力出口。

04 / 身份传递

传递可信上下文，逐层作出授权判断。

身份字段描述用户；凭据与可信绑定证明来源。工具参数由模型提出，身份与权限由可信服务端管理。

  1. 1
    企业身份体系认证企业用户
    已认证
  2. 2
    AI Gateway身份映射、能力授权、会话初始化
    可信映射
  3. 3
    DSH 与调用适配选择工具；可信适配层绑定身份上下文
    发起调用
  4. 4
    MCP Gateway凭据、工具权限与策略检查
    调用获准
  5. 5
    MCP 服务与业务系统执行数据范围与业务规则
    业务校验
  6. 6
    结果返回与审计返回获准结果，关联调用记录
    返回结果

示意结果 · 未发起真实请求

通过网关，再执行业务校验

当前身份具备数据查询能力；业务服务仍按用户的数据范围与规则执行查询。

每一跳都要保留可信用户关联，工具可见性之外仍需服务端授权。原文 §3、§5；可信绑定与凭据安全边界为图解整理补充。签发方、目标资源、有效期和下游认证方式尚待确定。

06 / 方案取舍

从快速接入，走向集中治理。

原文比较三种组织方式：目标采用 MCP Gateway；前两种方式作为验证与中间阶段选项。

方案一 · 快速验证

工具元信息

工具调用元信息（Tool Metadata）携带用户字段。

DSH→用户字段→MCP
收益
实现简单，开发成本低。
代价
字段的可信来源须另行建立；治理容易分散。

适合受控的概念验证（Proof of Concept，PoC）：先验证能力能否接通。

方案二 · 中间阶段

访问令牌

访问令牌（Access Token）承载目标资源的调用授权。

AI 网关→凭据适配→MCP
收益
可衔接企业服务认证方式。
代价
各服务仍需校验目标资源、权限与有效期；治理较分散。

原文称“Authorization Token 透传”；实际凭据机制仍待确定。

方案三 · 目标采用

MCP Gateway

将多能力服务的共性调用治理集中到出口。

DSH→MCP 网关→多 MCP
收益
统一校验、工具授权、审计与限流。
代价
增加网关建设、部署与运维复杂度。

适合多系统接入与统一治理的目标方向。

两个不同维度令牌是身份凭据，网关是治理落点；Gateway 方案仍可使用令牌。目标资源凭据须正确校验，不能把面向其他服务的令牌直接原样转发。
本设计选择集中治理，同时保留分阶段接入路径。原文 §5；令牌与网关的维度区分、安全限定为整理补充，官方依据见“设计原文与补充依据”。

07 / 分阶段建设

先验证接通，再按需求增加治理。

以下为演进设计，不表示当前实施进度；目标架构与每一期的建设范围分别表达。

第一阶段 · 目标：验证企业能力可被调用
AI Gateway→DSH Runtime→知识库／问数 MCP

重点验证接入链路

身份接入、插件加载、知识库调用和问数调用。

落地需要明确

第一阶段尚未增加 MCP Gateway；身份校验、工具授权和调用审计仍要有承载位置，具体分工待确认。

第一阶段直连验证，第二阶段引入网关，与最终目标一致。原文 §6。阶段进入条件、产品选型、部署方式与验收标准尚未确定。

08 / 决策归纳

架构方向已选，实现契约仍需明确。

备忘录已确定

保留清楚的职责边界

  1. AI Gateway 复用企业身份，承接能力授权。
  2. DSH 保持通用执行，行业能力通过扩展接入。
  3. MCP Gateway 作为目标架构的安全出口。
  4. 知识库、问数、业务 MCP 连接各自已有系统。
  5. 按接入验证、企业治理、行业平台逐步演进。
